# Security model

## Threat model

Jobs from different projects share a runner host. A job may run arbitrary code as root **inside
its own VM**. It must not be able to:

- read or change another job's code, secrets (e.g. `CI_JOB_TOKEN`, masked variables) or results;
- reach the runner host's services or the microVM control plane;
- leave anything behind for the next job.

## Controls

| Boundary | Control |
|---|---|
| Job ↔ job | one Firecracker VM (own kernel) per job, never reused; frames between microVM taps are dropped on the bridge (`table bridge firerunner`) |
| Job → host | nftables `table inet firerunner`: from the bridge only DHCP, DNS, the image cache and the `cache:` store are accepted (IPv4 and IPv6); IPv6 is disabled on the bridge |
| Host → job identity | each VM gets its own SSH host key, generated by the host and injected at boot; every connection pins it (`StrictHostKeyChecking=yes`, `HostKeyAlias=<vm id>`), so scripts and secrets only go to the VM created for the job |
| Job ↔ job bookkeeping | `CI_JOB_ID` must be numeric; the job state file is created exclusively, so one job can never take over another job's VM binding |
| Local users → control plane | flintlockd listens on 127.0.0.1 with a token stored in a root-only config file (not in argv); the daemon socket is root-only |
| Secrets on the host | runner token passed to gitlab-runner via the environment and stored 0600; `DOCKER_AUTH_CONFIG` is piped into the VM, never written to the host |
| Resource exhaustion | memory admission (no over-commit), bounded VM sizes, `OOMPolicy=continue` for flintlockd |
| Supply chain | every download checksum-verified; release binaries have an SPDX SBOM and a signed build provenance; CI actions pinned by SHA; govulncheck and golangci-lint on every push |

## Audit

The code was reviewed with [cloudflare/security-audit-skill](https://github.com/cloudflare/security-audit-skill)
(quick profile, source-only). No vulnerability was confirmed. Four leads that needed runtime facts
were fixed regardless and verified on a test host:

1. guest SSH identity not pinned on a shared bridge → per-VM pinned host keys + bridge isolation;
2. IPv4-only host filter → `inet` table, IPv6 disabled on the bridge;
3. flintlock token visible in the process list → config file;
4. unvalidated `CI_JOB_ID` in a host path → numeric-only, exclusive state file.

## Known gaps

- Guests can reach your LAN through NAT (same as docker executor bridge networking). If jobs must
  not reach internal networks, add a forward/egress policy for `10.200.0.0/24` on the host.
- `cache:` is stored per project (`runner/<runner>/project/<id>/<key>`); jobs only get presigned
  URLs for their own project's keys from gitlab-runner, the S3 keys stay on the host.
- Jobs of the same host share the Docker Hub pull-through cache. Deletes are disabled; that the
  registry's proxy mode also rejects pushes from jobs has not been independently verified yet.
